# Tasks — Query Endpoint

Decomposição do [`plan.md`](./plan.md) em tasks atômicas. Cada task é implementável e testável de forma independente, dentro da estrutura do Anexo C (`src/functions/query/`, `src/services/`, `src/shared/`).

**Estimativa:** P (≤½ dia) · M (½–1 dia) · G (>1 dia).

| ID | Descrição | Critérios de aceite (verificáveis) | Dependências | Est. |
|----|-----------|------------------------------------|--------------|------|
| **QE-02** | Tipos do domínio e erros compartilhados: `QueryRequest`, `QueryResponse`, `RetrievedChunk`, `SourceDocument` em `src/shared/types.ts`; `ValidationError` e `UpstreamError` em `src/shared/errors.ts`. | `npm run build` compila sem erro em modo strict. `QueryResponse` tem `answer: string` e `source_document: SourceDocument`. `RetrievedChunk` tem `id`, `content`, `source_document`, `score`. | — | P |
| **QE-01** | Setup do endpoint + validação de input: registrar a Azure Function v4 `POST /api/query` (`app.http`); schema Zod do body; handler retorna **400** com corpo de erro estruturado para body inválido e **200** para body válido (resposta ainda placeholder — busca/completion são tasks posteriores). | Body sem `question` → **400** com `{ error: string }`. `question` não-string ou vazia/só-espaços → **400**. Body JSON malformado → **400** (não 500). Body válido (`{ "question": "x" }`) → **200** com `answer` e `source_document` no shape de `QueryResponse`. | QE-02 | P |
| **QE-03** | Recuperação de chunks (Azure AI Search): interface `SearchService.retrieve(question): Promise<RetrievedChunk[]>` em `src/services/search.ts`, retornando os top-5 por similaridade. Implementação real adiada; stub em memória (lê `data/retrieval-corpus`) para teste. | Casos do mapa de cobertura (Anexo B): "Frete 600kg Manaus" → ≤5 chunks incl. `PROC-042v2-A`+`PROC-042v2-B`; "SLA do Platinum" → `SLA-2024-A` (que afirma só existirem 3 tiers); "Frete 300kg Salvador" (frete padrão <500kg) → **nenhum chunk relevante** (lista vazia ou só baixa relevância). Cada chunk tem `score` numérico decrescente. | QE-02 | M |
| **QE-04** | Montagem do prompt respeitando context budget (ADR-0002): `src/services/prompt-builder.ts` monta `system (~4K) + chunks (~8K, máx. 5) + pergunta`. Trunca/descarta chunks que estourem o orçamento. | Com 10 chunks de entrada, o prompt final inclui no máximo 5 e o total estimado de tokens de chunks ≤ ~8K. O system prompt vem de `/prompts/system-prompt.md`. Função é pura (mesma entrada → mesma saída). | QE-02, QE-03 | M |
| **QE-05** | Chamada ao modelo + retry: interface `CompletionService.complete(prompt): Promise<string>` em `src/services/completion.ts`, com retry exponencial (máx. 3 tentativas) para erros transitórios. | Em sucesso, retorna o texto do modelo. Em erro transitório (ex.: 429/503), refaz até 3× com backoff crescente; após esgotar, lança `UpstreamError`. Teste com stub que falha N vezes verifica a contagem de tentativas. | QE-04 | M |
| **QE-06** | Response builder com `source_document` (ADR-0003): `src/functions/query/response-builder.ts` monta o `QueryResponse` citando a fonte. Quando há versões contraditórias (v1 vs v2), cita a de vigência mais recente. | A resposta sempre inclui `source_document` não vazio. Casos (Anexo B): PROC-042 v1+v2 ("multiplicador do Sudeste") → cita **v2** (1.1, não 1.0); "SLA do Platinum" → resposta nega o tier (só Gold/Silver/Standard), fonte `SLA-2024-A`; "Frete 300kg Salvador" (sem cobertura) → `answer` diz que **não encontrou**, sem inventar valor. | QE-02, QE-05 | P |
| **QE-07** | Logging estruturado (pino): `src/shared/logger.ts`; instrumentar o handler com log de entrada, latência e erros — sem `console.log`. | Cada requisição emite um log JSON com `requestId`, `route` e `durationMs`. Nenhum `console.log` no código (verificável por lint/grep). Erros logados com nível `error` e a causa. | QE-01 | P |
| **QE-08** | Composição do handler (wire-up): injetar `SearchService`, `prompt-builder`, `CompletionService` e `response-builder` no fluxo do handler, substituindo o placeholder da QE-01 pela resposta real. | Body válido → **200** com resposta derivada dos chunks recuperados e `source_document` correto. Erro de upstream → **502/503** (não 500 genérico). Teste de integração com stubs cobre o caminho feliz e o de falha. | QE-01, QE-03, QE-04, QE-05, QE-06 | M |

## Ordem de execução sugerida

`QE-02` → `QE-01` → (`QE-03`, `QE-04`, `QE-05`, `QE-06` em paralelo conforme deps) → `QE-07` → `QE-08`.
